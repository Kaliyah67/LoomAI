# LoomAI Flash 长期记忆（Long-term Memory）改造方案

> **目标**：在不破坏现有任何功能的前提下，为 Flash 智能助手新增「真正意义上的长期记忆」能力。当用户说出值得记住的信息（如「我是一名 Java 后端开发」）时，系统由 LLM 自动判断是否值得记忆 → 抽取结构化记忆 → 存入 ChromaDB（复用现有向量库，新建独立 collection）→ 下次对话时按相关度检索并注入 prompt，实现跨会话的个性化记忆。

> **核心红线（必须遵守）**：现有功能零改动，所有扩展均以「新增文件」或「仅在现有文件末尾/指定位置追加」的方式落地，改动最小化、可一键回滚。记忆功能任何异常只打日志、绝不阻断聊天主链路。

---

## 0. 核心原则

1. **零破坏**：不改动 RAG、短期记忆、用户画像、图片编辑/合并等任何现有能力的既有逻辑与数据；新增能力完全独立。
2. **最小改动**：长期记忆完全落在 Python AI 侧（`loomai-agent`），**Java 侧零改动**（Java 已在请求体里传 `userId`，只是 Python 之前没读）。
3. **简单可运行**：只做「抽取 → 存储 → 检索 → 注入」单链路，不做多智能体记忆、记忆图谱、知识图谱、复杂层级、记忆固化、遗忘算法、独立记忆微服务、新 MQ、新 DB、新向量库、复杂重排。
4. **失败隔离**：记忆的抽取 / 存储 / 检索任一步失败，均 `print` 日志后静默降级，聊天照常输出。
5. **异步不阻塞**：记忆抽取 + 入库放在后台线程，绝不阻塞 SSE 首 token 与流式输出。
6. **可回滚**：记忆开关由环境变量 `LTM_ENABLED` 控制，置 `false` 即完全退回到现状。

## 2. 技术选型

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 长期记忆存哪 | ChromaDB（新建 collection `user_long_term_memory`） | 复用现有 `DashScopeEmbeddingFunction` + `CHROMA_DIR`，零新依赖、零新服务；语义检索「相关记忆」而非全量 |
| 向量化 | 复用 `DashScopeEmbeddingFunction`（`text-embedding-v3`, 1024 维） | 与 RAG 一致，成本低，无需引入新模型 |
| 是否值得记忆 + 抽取 | LLM（`qwen-plus`）一次性 JSON 输出 | 复用已有 LLM，prompt 返回结构化字段，简单可控 |
| 记忆类型 | 枚举 `preference / fact / goal / interest / experience / other` | 覆盖需求，仅作 metadata 标注，不做复杂分层 |
| 用户隔离 | ChromaDB `where={"user_id": str(userId)}` 元数据过滤 | ChromaDB 原生支持，严格隔离、零额外改造 |
| 去重（最低要求） | 内容完全相同去重（先查后写） | 满足「防止完全重复保存」的最低要求，简单稳定 |
| 异步 | Python `threading.Thread`（`daemon=True`） | 复用已 import 的 `threading`，不引入 MQ/线程池，不阻塞聊天 |
| 开关 | 环境变量 `LTM_ENABLED`（默认 `true`） | 一键关闭回滚 |

**明确不做**：多智能体记忆、记忆图谱/知识图谱、复杂记忆层级、记忆固化/衰减、遗忘算法、独立记忆微服务、新 MQ、新 DB、新向量库、复杂 reranker、记忆的「更新/合并」复杂逻辑（只做基础去重）。

## 3. 改造后整体架构与数据流

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                           Python AI 侧（loomai-agent）                        │
│                                                                             │
│  /api/chat (server.py)                                                      │
│   │  ① 读 message / sessionId / profile / userId                            │
│   │  ② 短期记忆：ChatMemoryStore(Redis, TTL 2h)                             │
│   │  ③ RAG：retrieve_advanced(message, history)  → 搭配知识                   │
│   │  ④ 长期记忆：long_term_memory.retrieve_memories(user_id, message)        │
│   │        └─ 语义检索 + where 用户隔离 → 相关记忆 Top N                       │
│   │  ⑤ 画像：profile(style/color/bodyType)                                   │
│   │  ⑥ 组装 prompt：System → Profile → 长期记忆 → RAG → 短期记忆 → Message    │
│   │  ⑦ 流式生成（Generation.call stream=True）                               │
│   │  ⑧ 后台线程：extract_and_save(user_id, message, ai_text)                 │
│   │        └─ LLM 判断 should_remember + 抽取 → 去重 → ChromaDB 入库          │
└─────────────────────────────────────────────────────────────────────────────┘
              ▲ HTTP(S) body: {userId, sessionId, message, profile}
┌─────────────────────────────────────────────────────────────────────────────┐
│        Java 侧（已传 userId，零改动）→ FlashController → FlashServiceImpl      │
└─────────────────────────────────────────────────────────────────────────────┘
```

**数据流（一次对话）**：

1. 前端 `FlashView` → Java `FlashController.chat()`（JWT 解析出 `userId`）。
2. `FlashServiceImpl.streamChat()` 把 `userId/sessionId/message/profile` POST 到 Python `/api/chat`。
3. Python `chat_api()` 依次准备：短期记忆摘要 → RAG 知识 → **长期记忆（新增）** → 画像 → 组装系统提示。
4. LLM 流式生成，token 经 SSE 透传回前端。
5. 生成结束后，**后台线程**异步执行「抽取 + 入库」，不影响已完成的响应。

## 5. 评估一：现有 ChromaDB 是否可直接复用

**结论：可以直接复用，但必须新建独立 collection。**

| 复用点 | 是否可复用 | 说明 |
|--------|-----------|------|
| `DashScopeEmbeddingFunction`（`text-embedding-v3`, 1024 维） | ✅ 直接复用 | 与 RAG 同一 embedding，语义一致 |
| `CHROMA_DIR`（`chroma_db/` 持久化目录） | ✅ 直接复用 | 同一个 `PersistentClient` 下并存多个 collection，无需新目录 |
| `collection = "fashion_knowledge"` | ❌ 不复用 | 记忆若混入 RAG 集合，会污染 `retrieve_advanced` 的召回结果 |

**隔离方式**：`get_or_create_collection(name="user_long_term_memory", ...)`，与 `fashion_knowledge` 同库不同集合，逻辑完全隔离。检索时各自只查各自的 collection，互不干扰。

**复用价值**：零新依赖（`chromadb` 已装）、零新模型、零新服务，长期记忆的「向量化 + 存储 + 相似度检索」全部白嫖现有 RAG 底座。

## 6. 评估二：User Profile 与 Long-term Memory 如何共存

**结论：两者定位不同、存储不同、天然互补，不需要动 Profile，也不冲突。**

| 维度 | User Profile（现有） | Long-term Memory（新增） |
|------|---------------------|--------------------------|
| 存储 | MySQL `user_profile` 表 | ChromaDB `user_long_term_memory` |
| 数据结构 | 固定三字段 `style/color/bodyType` | 自由文本 + `memory_type` 标签 |
| 写入方式 | 用户**手动设置** | LLM **自动抽取** |
| 内容粒度 | 粗粒度「穿搭偏好」 | 任意值得记住的个性化事实/偏好/目标/经历 |
| 更新方式 | `saveOrUpdate` 覆盖 | 追加（+ 基础去重） |
| 生命周期 | 常驻，需用户主动改 | 随对话自动累积 |

**共存策略**：

- Profile 继续承担「用户显式设定的穿搭偏好」，prompt 里仍是独立一段（位置不变）。
- Long-term Memory 承担「对话中自动沉淀的个性化信息」，prompt 里作为**新的一段**插在 Profile 之后。
- 二者不互相删除、不互相替换、不合并数据；即使长期记忆功能关闭（`LTM_ENABLED=false`），Profile 逻辑不受任何影响。

## 7. 六大能力落地对照

| 需求能力 | 落地方式 |
|---------|---------|
| ① 自动抽取（LLM 判断 `should_remember` + 抽取） | `_extract_memory`：prompt 要求 LLM 返回 JSON，`should_remember=false` 时不入库 |
| ② 简单记忆类型 | `MEMORY_TYPES = [preference, fact, goal, interest, experience, other]`，存 metadata |
| ③ 存 ChromaDB（复用 + 严格用户隔离） | 新建 collection + `where={"user_id": str(user_id)}` + 完整 metadata |
| ④ 检索（相关记忆，非全量） | `retrieve_memories(user_id, query, top_k)` 语义检索 Top N |
| ⑤ 与 User Profile 共存 | 不动 Profile，prompt 中独立段落（见 §6） |
| ⑥ 不做复杂更新，但基础去重 | `_dedup`：精确内容匹配命中即跳过（最低要求） |

## 8. Prompt 注入设计

**注入顺序**（适配现有 `context_parts` 组装顺序）：

```
System Prompt（Flash 角色设定）
  → Profile（用户画像）
  → Long-term Memory（关于你的长期记忆）   ← 新增
  → RAG（可参考的搭配知识）
  → Short-term Memory（之前的对话摘要）
  → Message（当前用户消息）
```

**注入文本格式**：

```
关于你的长期记忆：
- [preference] 用户偏好深色系、简约风格。
- [fact] 用户是一名 Java 后端开发，日常通勤对着装要求偏商务休闲。
```

只注入「与当前问题语义相关的 Top N 条」，避免无关记忆稀释 prompt；`top_k` 由 `LTM_TOP_K` 控制（默认 3）。

---

## 9. 异步与失败隔离

- **异步**：`extract_and_save` 内部用 `threading.Thread(target=..., daemon=True).start()` 后台执行，抽取 + 入库不阻塞流式输出；抽取动作发生在 AI 回复生成**之后**，天然不拖慢首 token。
- **失败隔离**：`retrieve_memories` / `extract_and_save` 全函数 `try/except`，异常仅 `print`，返回空列表 / 静默跳过；`chat_api` 里的调用点也各自 `try/except`。**任何记忆异常都不会让 `chat_api` 返回 500，聊天照常流式。**

## 11. 降级机制

| 场景 | 降级行为 |
|------|---------|
| `LTM_ENABLED=false` | 检索与抽取全部跳过，等同现状 |
| ChromaDB 读写异常 | `print` 日志，检索返回空、抽取跳过，聊天照常 |
| LLM 抽取异常 / 返回非法 JSON | 丢弃本次抽取，不影响已完成的回复 |
| `userId` 缺失（未登录/异常请求） | `user_id=None`，跳过记忆（有 `and user_id is not None` 判断） |
| 抽取线程异常 | 后台线程 `daemon` + 内部 `try/except`，不影响主线程 |

## 14. 面试话术

> **Q：Flash 的长期记忆是怎么做的？**
>
> 长期记忆是在原 Flash 对话基础上新增的能力，分「抽取」和「注入」两条链路：
> - **抽取**：用户每轮对话结束后，后台线程让 LLM 判断这轮是否包含值得记住的信息（`should_remember`），值得的话抽取成带类型的结构化记忆（偏好/事实/目标/兴趣/经历等）。
> - **存储**：抽出的记忆向量化后写入 ChromaDB 的**独立 collection**（`user_long_term_memory`），与 RAG 知识库（`fashion_knowledge`）物理同库、逻辑隔离，避免互相污染；`metadata` 里带 `user_id` 做严格用户隔离。
> - **注入**：下次对话时，按当前 query 语义检索「与该用户相关的 Top N 条记忆」，作为独立一段插到系统提示里（顺序是 System → 画像 → 长期记忆 → RAG → 短期记忆 → 消息）。
>
> 设计上强调三点：**异步**（抽取入库走后台线程，不阻塞流式）、**失败隔离**（记忆任何异常只打日志、绝不打断聊天）、**可回滚**（一个环境变量就能整体关闭）。

> **Q：为什么不直接存 MySQL，而用 ChromaDB 存长期记忆？**
>
> 因为记忆的召回是「按语义相关性」的——用户这轮问「面试穿什么」，需要召回的是「我是 Java 后端、偏商务休闲」这类语义相关记忆，而不是把所有记忆全量塞进 prompt。向量检索天然适合这个场景，而且 RAG 已经搭好了 ChromaDB + DashScope embedding 的底座，直接复用零成本。MySQL 的 `user_profile` 则继续承担「用户手动设定的固定三字段偏好」，两者定位互补、不冲突。

> **Q：怎么保证用户之间的记忆隔离？**
>
> 存储时把 `userId` 写进每条记忆的 `metadata`，检索时用 ChromaDB 的 `where={"user_id": ...}` 做过滤，只有当前用户自己的记忆能被召回，从数据层就隔离了。

## 17. 风险与对策

| 风险 | 对策 |
|------|------|
| 抽取 prompt 返回非法 JSON | 解析失败静默丢弃，不影响回复；prompt 里强约束「只输出 JSON」 |
| 记忆数量随对话增长膨胀 | 每次仅注入语义相关 Top N（默认 3），不随总量线性增长 |
| 误记无关信息 | LLM `should_remember` 判断 + 只抽取高置信记忆；类型标签便于后续治理 |
| 与 RAG 混淆 | 独立 collection，检索各自隔离 |
| 影响聊天延迟 | 检索轻量（Top N 向量查询）、抽取走后台线程，不阻塞流式 |
