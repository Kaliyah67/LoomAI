# 服务熔断降级改造方案（Java ↔ Python 异构服务）

> 目标：在**不破坏现有图片编辑、图片合并、图片搜索、图片上传等已有功能**的前提下，为 Java 后端调用 Python AI 侧车服务（`127.0.0.1:5000`）的链路增加**超时 + 熔断 + 降级**三层保护，避免 Python 服务异常（挂掉 / 卡死 / 超时）时拖垮整个异步任务处理链路。
>
> ```
> 前端提交编辑/合并/搜索/上传
>    ↓
> FileController / FileServiceImpl
>    ↓
> RabbitMQ（task.edit / task.merge）—— 异步解耦
>    ↓
> TaskMessageConsumer.handleTask（@RabbitListener，prefetch=1）
>    ↓
> PythonAiIntegrationServiceImpl（RestClient 调 Python）
>    ↓
> ┌────────────── 熔断器 CircuitBreaker "pythonAi" ──────────────┐
> │  CLOSED   → 真实调用 Python（超时 connect 1s / read 60s）    │
> │  OPEN      → 直接降级（fallback），不再真调 Python           │
> │  HALF_OPEN → 放 1 个探测请求，成功回 CLOSED，失败继续 OPEN    │
> └─────────────────────────────────────────────────────────────┘
>    ↓
> Python Flask（127.0.0.1:5000）
> ```
>
> 升级后，Java 侧调用 Python 的 5 个接口（`edit` / `merge` / `search` / `registerUploadedImage` / `validateImage`）都套上熔断器并各自配置降级兜底，**其余业务逻辑保持原样**。

---

## 0. 核心原则（每次改动前先读这一节）

1. **现有功能零改动**：`PythonAiIntegrationServiceImpl` 里 5 个方法的「真实调用逻辑」一行不动，只在其外层加 `@CircuitBreaker` 注解 + 新增 fallback 方法；`TaskMessageConsumer` 的 `catch (Exception)` 已能把降级异常写入 `errorMessage`，无需改动。
2. **现有文件只「追加」不「重写」**：`PythonAiIntegrationServiceImpl` 只在方法上补注解 + 末尾追加 fallback 方法；`application.yml` 只在末尾追加配置段；`pom.xml` 只追加一个依赖。
3. **每层都有降级**：超时、熔断、降级三层任意一层生效，都不会让调用线程永久阻塞，任务最多快速标记 `FAILED`，**异步任务处理永不卡死**。
4. **回滚容易**：所有新增逻辑集中在「一个依赖 + 一个异常类 + 若干注解/fallback + yml 配置」，出问题直接去掉依赖和注解即可还原。
5. **技术方案以本方案为准**：本文档是熔断降级改造的最终约定，若与历史讨论冲突，以本文档为准。

## 1. 现状分析（改造前）

当前调用链（`loomai-main`，Java 侧）：

```text
TaskMessageConsumer.handleTask（MQ 消费者，prefetch=1 串行）
    ↓
PythonAiIntegrationServiceImpl.edit / merge（RestClient）
    ↓
Python Flask 服务（127.0.0.1:5000）
```

当前实现的主要特点（**保留作为基线，不要删除**）：

* 调用 Python 用 Spring 6 的 **`RestClient`**（`PythonAiIntegrationServiceImpl` 构造器里 `RestClient.builder().baseUrl(...).build()`）。
* 任务处理走 **RabbitMQ 异步解耦**：`FileServiceImpl.submitEditAsync/submitMergeAsync` 发消息 → `TaskMessageConsumer` 消费 → 调 Python。
* 消费者 `prefetch=1`，**串行处理**，同一时刻只有一个任务在调 Python。
* 任务状态流转：`PENDING → PROCESSING → SUCCESS / FAILED`，状态存在 Redis（TTL 1h）。

**当前缺失（改造点）：**

| 缺失环节 | 当前表现 | 导致的问题 |
|---------|---------|-----------|
| 调用超时 | `RestClient` 未配 `connectTimeout` / `readTimeout`（默认无限） | Python 挂掉/卡死时，消费者线程**永久阻塞**，后续消息全堆积在队列 |
| 熔断 | 无熔断器，每条消息都去撞已挂的 Python | 每次都等到超时（或永久阻塞），雪崩 |
| 降级 | 只有 `try-catch` 把失败标记 `FAILED`，未区分「AI 服务不可用」和「业务失败」 | 用户看到同一句报错，且线程先被卡死才标记失败 |

## 2. 技术选型（含选型原因）

| 环节 | 选型 | 说明 |
|------|------|------|
| 熔断器 | **Resilience4j**（`resilience4j-spring-boot3` 2.2.0） | Spring Boot 3 官方推荐的轻量容错库，注解式 + 配置化，适配 Boot 3.2 |
| 熔断实例 | 单一实例 **`pythonAi`** | 5 个接口都调同一个 Python 进程，Python 挂了应整体熔断，共用 1 个实例最贴合语义 |
| 超时实现 | `SimpleClientHttpRequestFactory` 设 `connectTimeout` / `readTimeout` | Spring 自带，无需额外依赖；`RestClient` 通过 `requestFactory(...)` 注入 |
| 降级异常 | 新建 `AiServiceUnavailableException extends RuntimeException` | 语义明确的降级异常，方便区分「服务不可用」和「业务失败」 |
| 熔断注解 | `@CircuitBreaker(name="pythonAi", fallbackMethod=...)` 加在**实现类方法**上 | Boot 默认 CGLIB 代理（`proxy-target-class=true`），AOP 能拦截到实现类方法上的注解 |

### 2.1 选型原因（为什么这么选）

* **为什么选 Resilience4j**：Spring Boot 3 官方文档推荐的容错库，轻量（不像 Hystrix 已停止维护、Sentinel 偏重）。注解式 `@CircuitBreaker` + `application.yml` 配置即可，无需手写状态机。项目已依赖 `spring-boot-starter-aop`，注解切面天然可用。
* **为什么熔断实例用单一 `pythonAi`**：`edit` / `merge` / `search` / `upload` 都打同一个 Python 服务（同进程、同 base-url）。Python 进程挂了，任何接口都会失败，所以「整体熔断」比「每个接口一个实例」更贴合真实故障模型，也更好维护。
* **为什么必须先用 `SimpleClientHttpRequestFactory` 配超时**：`RestClient` 默认没有超时限制，Python 一旦无响应，调用会无限挂起。**没有超时，熔断器连「失败」都感知不到**（失败是熔断统计的输入），所以超时是熔断的前提。
* **为什么 readTimeout 设 60s**：图片编辑/合并走 DashScope 多模态模型，单次生成通常 10~60s，60s 是当前项目的**初始经验值**，既给足生成时间、又能兜底卡死场景。后续按实际生成耗时调优。
* **为什么降级要区分接口**：`edit/merge` 是异步重任务（结果进查询页），降级应标记 `FAILED` 让用户看到友好文案；`search` 是同步检索（降级返回空列表即可，不抛 500）；`validateImage` / `registerUploadedImage` 是非核心辅助（降级应放行/跳过，不挡主流程）。见 §6。

## 3. 改造后整体架构（完整链路）

```text
TaskMessageConsumer.handleTask
    ↓
PythonAiIntegrationServiceImpl.edit / merge / search / ...
    ↓
【熔断器 CircuitBreaker "pythonAi"】 三态
    ├─ CLOSED（正常）：放行请求，RestClient 调 Python，统计成功/失败
    ├─ OPEN（熔断）：快速失败，走 fallback 降级，不再真调 Python
    └─ HALF_OPEN（半开）：放 1 个探测请求，成功 → CLOSED，失败 → OPEN
    ↓
真实调用：RestClient（connectTimeout 1s / readTimeout 60s）→ Python Flask
    ↓
失败/降级：fallback 方法
    ├─ edit / merge       → 抛 AiServiceUnavailableException → 消费者标记 FAILED
    ├─ search             → 返回 List.of()
    ├─ registerUploadedImage → 返回 Optional.empty()
    └─ validateImage      → 返回 true（放行）
```

> 说明：熔断统计的是「真实调用 Python」的成功/失败。熔断打开后，`@CircuitBreaker` 不再执行原方法体，直接走 fallback，因此线程不会阻塞、队列不会堆积。

## 4. 第一层：超时（熔断的前提）

给 `PythonAiIntegrationServiceImpl` 构造器里的 `RestClient` 注入带超时的 `requestFactory`。

```java
SimpleClientHttpRequestFactory factory = new SimpleClientHttpRequestFactory();
factory.setConnectTimeout(properties.getConnectTimeout());  // 建立连接 1s
factory.setReadTimeout(properties.getReadTimeout());        // 读取响应 60s

this.restClient = RestClient.builder()
        .baseUrl(trimTrailingSlash(properties.getBaseUrl()))
        .requestFactory(factory)
        .build();
```

`PythonAiServiceProperties` 新增两个可配置字段（带默认值）：

```java
private Duration connectTimeout = Duration.ofSeconds(1);
private Duration readTimeout = Duration.ofSeconds(60);
```

> **为什么 1s / 60s**：连接是本地 `127.0.0.1`，1s 足够（连不上说明 Python 根本没起来）；读取要给 AI 生成图留足时间，60s 是初始经验值。两者都做成配置项，便于部署时调整。

## 5. 第二层：熔断器（Circuit Breaker）

### 5.1 熔断三态

```text
        ┌───────────────────────────────┐
        │         CLOSED（闭合）          │
        │   正常放行，统计成功/失败        │
        └───────────────┬───────────────┘
                        │ 失败率达到阈值（10 次里 50%）
                        ▼
        ┌───────────────────────────────┐
        │         OPEN（打开）            │
        │  快速失败，不再真调 Python      │
        │  持续 wait-duration 30s        │
        └───────────────┬───────────────┘
                        │ 30s 后进入半开
                        ▼
        ┌───────────────────────────────┐
        │       HALF_OPEN（半开）         │
        │  放 1 个探测请求                │
        │  成功 → CLOSED / 失败 → OPEN    │
        └───────────────────────────────┘
```

* **CLOSED**：熔断器闭合，请求正常放行，同时统计窗口内的成功/失败次数。
* **OPEN**：失败率达到阈值，熔断器打开，后续请求直接走 fallback 快速失败，**不再发起真实调用**。
* **HALF_OPEN**：OPEN 持续一段时间后，放行 1 个请求作为探测。若成功则回到 CLOSED，若失败则重新 OPEN。

### 5.2 配置（`application.yml` 追加）

```yaml
resilience4j:
  circuitbreaker:
    instances:
      pythonAi:
        sliding-window-size: 10                          # 滑动窗口大小（最近 10 次调用）
        failure-rate-threshold: 50                       # 失败率阈值（10 次里 ≥ 50% 打开）
        wait-duration-in-open-state: 30s                 # OPEN 持续 30s 后进入半开
        permitted-number-of-calls-in-half-open-state: 1  # 半开时放 1 个探测请求
        minimum-number-of-calls: 5                       # 至少 5 次调用才开始统计失败率
```

> 以上参数是当前项目的**初始配置**，不是行业强制标准；`failure-rate-threshold`、`wait-duration` 需按实际故障频率调优。

## 6. 第三层：降级 Fallback

熔断打开（或真实调用失败）时，`@CircuitBreaker` 走 `fallbackMethod`。按接口重要性区别对待：

| 方法 | 返回类型 | 降级行为 | 为什么 |
|------|---------|---------|--------|
| `edit` | `EditImageResponse` | fallback 抛 `AiServiceUnavailableException("AI 服务暂不可用，请稍后重试")` | 异步重任务，让消费者标记 `FAILED`，结果查询页显示友好文案 |
| `merge` | `MergeImageResponse` | 同上 | 同上 |
| `search` | `List<SearchImageResponse>` | fallback 返回 `List.of()` | 同步检索，返回空列表，前端显示「暂无结果」，不抛 500 |
| `registerUploadedImage` | `Optional<PythonUploadImageResponse>` | fallback 返回 `Optional.empty()` | 上传后的向量登记，非核心，跳过即可（调用方已忽略返回值） |
| `validateImage` | `boolean` | fallback 返回 `true` | 上传前的图片审核，非核心校验，Python 挂了应**放行**而非拒绝上传 |

### 6.1 注解与 fallback 代码（追加到 `PythonAiIntegrationServiceImpl`）

5 个方法在原方法签名上补 `@CircuitBreaker`，并在类末尾追加对应 fallback 方法：

```java
@CircuitBreaker(name = "pythonAi", fallbackMethod = "editFallback")
public EditImageResponse edit(EditImageRequest editImageRequest) { /* 原方法体不变 */ }

public EditImageResponse editFallback(EditImageRequest request, Throwable t) {
    log.warn("编辑图片降级：AI 服务暂不可用, err={}", t.getMessage());
    throw new AiServiceUnavailableException("AI 服务暂不可用，请稍后重试");
}

@CircuitBreaker(name = "pythonAi", fallbackMethod = "mergeFallback")
public MergeImageResponse merge(MergeImageRequest mergeImageRequest) { /* 原方法体不变 */ }

public MergeImageResponse mergeFallback(MergeImageRequest request, Throwable t) {
    log.warn("合并图片降级：AI 服务暂不可用, err={}", t.getMessage());
    throw new AiServiceUnavailableException("AI 服务暂不可用，请稍后重试");
}

@CircuitBreaker(name = "pythonAi", fallbackMethod = "searchFallback")
public List<SearchImageResponse> search(Long userId, SearchImageRequest request) { /* 原方法体不变 */ }

public List<SearchImageResponse> searchFallback(Long userId, SearchImageRequest request, Throwable t) {
    log.warn("图片搜索降级：AI 服务暂不可用, err={}", t.getMessage());
    return List.of();
}

@CircuitBreaker(name = "pythonAi", fallbackMethod = "registerUploadedImageFallback")
public Optional<PythonUploadImageResponse> registerUploadedImage(Long userId, String ossUrl) { /* 原方法体不变 */ }

public Optional<PythonUploadImageResponse> registerUploadedImageFallback(Long userId, String ossUrl, Throwable t) {
    log.warn("图片向量登记降级：AI 服务暂不可用, err={}", t.getMessage());
    return Optional.empty();
}

@CircuitBreaker(name = "pythonAi", fallbackMethod = "validateImageFallback")
public boolean validateImage(Path filePath) { /* 原方法体不变 */ }

public boolean validateImageFallback(Path filePath, Throwable t) {
    log.warn("图片审核降级：AI 服务暂不可用，放行, err={}", t.getMessage());
    return true;
}
```

### 6.2 降级异常类（新建）

```java
package com.lsq.exception;

/**
 * AI 服务不可用异常：熔断打开或降级时抛出，
 * 用于让上游任务标记 FAILED 并给出友好提示。
 */
public class AiServiceUnavailableException extends RuntimeException {
    public AiServiceUnavailableException(String message) {
        super(message);
    }
}
```

> `TaskMessageConsumer.handleTask` 现有 `catch (Exception e)` 已捕获此异常，`updateTaskStatus(taskId, "FAILED", ..., e.getMessage())` 会把「AI 服务暂不可用，请稍后重试」写入 Redis，前端结果查询页直接显示。

## 8. 降级机制总表（任一环节失败不拖垮任务）

| 故障/环节 | 降级行为 |
|-----------|---------|
| Python 连接超时（1s 内连不上） | `RestClient` 抛异常 → 记一次失败 → 达到阈值后熔断 |
| Python 读取超时（60s 无响应） | 同上，记一次失败 |
| 熔断打开（连续失败达阈值） | 直接走 fallback，不再真调 Python |
| `edit` / `merge` 失败/降级 | 抛 `AiServiceUnavailableException` → 消费者标记 `FAILED`，结果查询页显示友好文案 |
| `search` 失败/降级 | 返回 `List.of()`，前端「暂无结果」 |
| `registerUploadedImage` 失败/降级 | 返回 `Optional.empty()`，跳过登记 |
| `validateImage` 失败/降级 | 返回 `true` 放行，不挡上传主流程 |
| 半开探测成功 | 自动回 CLOSED，无需人工干预 |

**核心结论**：三层保护（超时 → 熔断 → 降级）是「渐进增强」，任何一层生效都会让「Python 挂了」这个故障**最多表现为任务快速 FAILED**，**绝不会让 MQ 消费者线程永久卡死、队列堆积、整条链路雪崩**。

## 10. 改造前后对比

### 改造前

```text
TaskMessageConsumer
    ↓
RestClient（无超时）→ Python
    ↓
Python 挂了 → 消费者线程永久阻塞 → 队列堆积 → 雪崩
```

### 改造后

```text
TaskMessageConsumer
    ↓
RestClient（connect 1s / read 60s）
    ↓
熔断器 CircuitBreaker "pythonAi"
    ├─ CLOSED   → 正常调用
    ├─ OPEN     → 快速失败（fallback 降级）
    └─ HALF_OPEN → 探测恢复
    ↓
失败最多标记 FAILED，绝不卡死队列
```

### 每个组件解决的问题

| 组件 | 解决的问题 |
|------|-----------|
| 调用超时 | Python 无响应时线程永久阻塞 |
| 熔断器 | Python 连续失败后仍反复调用导致雪崩 |
| 降级 Fallback | 熔断时给出友好结果而非卡死/脏数据 |

## 11. 面试话术

> "我这个项目是 Java（Spring Boot）和 Python（Flask）的异构架构：Java 是主服务，Python 作为侧车（sidecar）提供 AI 能力（图片编辑/合并走 DashScope 多模态，检索走向量）。两者之间通过 RestClient 走 HTTP，任务本身用 RabbitMQ 做了异步解耦。"

然后重点讲容错：

```text
Python 服务异常
    ↓
第一层：调用超时（connect 1s / read 60s，不让线程无限等）
    ↓
第二层：熔断（Resilience4j，失败率达阈值 → 打开，快速失败）
    ↓
第三层：降级（按接口区别：重任务标记 FAILED、检索返回空、非核心放行）
    ↓
故障恢复：半开探测 → 自动回闭合
```

重点让面试官听出来：

> **"我不是简单调一个 Python 接口就完事了，而是考虑了异构服务之间一旦故障怎么兜底——用「超时 + 熔断 + 降级」三层保证上游任务不会因为下游 Python 挂了而雪崩，M**Q 队列不堆积、线程不卡死，故障恢复后还能自动半开探测回正常。"**

## 12. 统一参数配置

```yaml
python:
  ai:
    base-url: http://127.0.0.1:5000
    enabled: true
    connect-timeout: 1s      # 连接超时
    read-timeout: 60s        # 读取超时（AI 生成图慢，给足）

resilience4j:
  circuitbreaker:
    instances:
      pythonAi:
        sliding-window-size: 10
        failure-rate-threshold: 50
        wait-duration-in-open-state: 30s
        permitted-number-of-calls-in-half-open-state: 1
        minimum-number-of-calls: 5
```

```text
连接超时        = 1s
读取超时        = 60s
滑动窗口        = 10 次
失败率阈值      = 50%
熔断持续时间    = 30s
半开探测数      = 1
最小调用数      = 5
```

> 以上参数都是当前项目的**初始配置**，不是绝对行业标准；`read-timeout` 需按 DashScope 实际生成耗时调优，`failure-rate-threshold` / `wait-duration-in-open-state` 需按实际故障频率调优。
