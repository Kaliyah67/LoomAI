# 第一部分：项目整体架构

---

## Q1：请用 3 分钟介绍你的项目整体架构

**推荐回答**：

这是一个智能服装搭配与多模态检索平台，采用 Java + Python 异构架构。前端用 Vue 3 + Element Plus；Java 端基于 Spring Boot 3.2 负责用户认证、业务编排、OSS 存储和 RabbitMQ 消息；Python 端基于 Flask 封装了 CLIP 模型推理、Qwen-VL 图片审核、LangChain Agent 工具调用等 AI 能力。中间件方面，MySQL 存储业务数据，Redis 承担 JWT 缓存、验证码、CLIP 向量和任务状态四种角色，RabbitMQ 实现 AI 编辑/合并任务的异步解耦。

**对应代码**：
- 文件：`docker-compose.yml`
- 说明：MySQL、Redis、RabbitMQ 三个容器构成基础设施层

**面试官继续追问**：这个架构是微服务吗？

**深入回答**：不是标准微服务。Java 和 Python 是主从关系（主控端+AI侧车），所有用户请求必经 Java 鉴权后才能调用 Python。Python 不能独立对外提供服务。这属于"异构混合架构"，选择它是因为 AI 生态在 Python 侧（LangChain、Transformers、CLIP），而业务层 Java 更稳定成熟。

## Q2：为什么采用 Java + Python 异构架构，而不是全部用 Java 或 Python？

**推荐回答**：

核心原因：**Java 不适合做 AI，Python 不适合做业务**。

具体来说：
1. LangChain、Transformers、CLIP、DashScope SDK 的生态全部在 Python，Java 没有可替代方案
2. Spring Boot 的鉴权、事务管理、MyBatis-Plus、RabbitMQ 集成在 Java 生态中最成熟
3. 分离后 AI 层可独立升级模型版本、扩展新工具，不影响主控端稳定性

**对应代码**：
- 文件：`loomai-main/src/main/java/com/lsq/service/impl/PythonAiIntegrationServiceImpl.java`
- 方法：`validateImage()`、`edit()`、`merge()`、`search()`
- 说明：Java 通过 RestClient HTTP 调用 Python，是所有跨语言通信的统一入口

**代码**：
```java
// Java 端统一通过 RestClient 调用 Python，不耦合具体 AI 逻辑
public PythonAiIntegrationServiceImpl(PythonAiServiceProperties properties, ...) {
    this.restClient = RestClient.builder()
            .baseUrl(trimTrailingSlash(properties.getBaseUrl()))
            .build();
}
```

**面试官继续追问**：Python 服务挂了，Java 会怎样？

**深入回答**：当前代码对每个 Python 接口调用都有 try-catch 兜底，不会让 Java 主流程崩溃。例如 `validateImage()` 失败返回 `false`（审核不通过），`registerUploadedImage()` 失败只打 warn 日志不阻塞上传流程。但 /api/skill/image 失败会向 Controller 抛异常，前端收到 500。

## Q7：用户登录的完整认证流程是怎样的？

**推荐回答**：

统一认证接口 `POST /api/user/auth`，用 `@` 符号区分两种方式：

1. **邮箱+验证码**（account 含 `@`）：生成 6 位随机码 → 存 Redis 5 分钟 → QQ SMTP 发送 → 新用户自动注册 → 返回 JWT
2. **用户名+密码**（account 不含 `@`）：BCrypt 密码校验 → 新用户自动注册 → 返回 JWT

JWT 本身有 expiration，同时存入 Redis `jwt:user:{userId}`，键值就是 token。同一用户多次登录复用已有 token。

**对应代码**：
- Controller：`UserController.java:39-42`
- Service：`UserServiceImpl.java:58-109`
- JWT 工具：`JwtUtil.java:45-76`
- 验证码：`VerificationCodeService.java:24-28`
- 邮件：`EmailService.java:22-37`

**面试官继续追问**：JWT 过期了怎么办？

**深入回答**：当前前端 `http.js` 的响应拦截器检测到 JWT 过期会清空 Pinia authStore 并跳转登录页（`router/index.js:30-38`）。但没有实现 Refresh Token 机制——推荐的优化是返回 short-lived access token + long-lived refresh token。

## Q9：Python 服务调用失败时，Java 端如何处理？

**推荐回答**：

四个接口的容错策略不同：

1. `validateImage()`：try-catch 后返回 `false`（等于拒绝上传，安全侧偏向拒绝）
2. `registerUploadedImage()`：catch 后只打 warn 日志，不影响上传成功返回——代价是该图片没有向量索引，搜不到
3. `search()`：catch 后返回空列表
4. `edit()` / `merge()`：catch 后向上抛出 RuntimeException，最终由 Controller 的 AOP 切面捕获返回 500

**对应代码**：
- 文件：`PythonAiIntegrationServiceImpl.java`

```java
// validateImage: 失败 = 拒绝 (safe side)
} catch (Exception e) {
    log.warn("validateImage 调用失败: {}", e.getMessage());
    return false;
}

// registerUploadedImage: 失败 = 静默跳过 (代价是搜索不到)
} catch (RestClientException e) {
    log.warn("调用 Python /api/upload-image 失败, userId={}: {}", userId, e.getMessage());
    return Optional.empty();
}

// edit/merge: 失败 = 抛异常 (阻塞业务)
} catch (RestClientException e) {
    throw new RuntimeException(e);
}
```

**面试官继续追问**：这种容错设计有什么问题？

**深入回答**：`registerUploadedImage` 失败了静默跳过，用户看到"上传成功"但搜索不到该图，数据一致性问题。应该加一个重试队列或异步补偿机制。

**对应代码**：

**面试官继续追问**：如果超时了，消息会丢失吗？

**深入回答**：同步调用超时会抛异常→AOP 切面捕获→返回 500。异步调用走 RabbitMQ 时，Consumer 里的 HTTP 调用超时会抛异常→被 `handleTask` 的 catch 捕获→更新 Redis 状态为 FAILED→消息被 auto-ack（因为没有手动 ACK），消息就丢了。正确做法是配置手动 ACK + nack 重新入队。

## Q14：Python 端 `server.py` 中 `_get_field_from_request()` 函数是做什么的？

**推荐回答**：

这是一个自定义参数提取器，用于兼容多种前端传参方式——同一字段前端有时放在 JSON body、有时放在 form-data、有时放 query string。函数按优先级从 JSON body → form → query string 中提取字段。

**对应代码**：
- 文件：`server.py:256-271`

```python
def _get_field_from_request(name: str, default=None):
    body = request.get_json(silent=True) or {}
    if name in body:
        return body.get(name, default)
    if name in request.form:
        return request.form.get(name, default)
    if name in request.args:
        return request.args.get(name, default)
    return default
```

这暴露了两个端通信时没有统一契约——Java 和 Python 开发者各自定义参数名（比如 `ossUrl` vs `oss_address` vs `oss_url`）。

## Q16：项目中为什么要引入 RabbitMQ？解决什么问题？

**推荐回答**：

图片编辑和合并需要调用 DashScope 的 `qwen-image-edit-plus` 模型，一次推理可能需要 30 秒到几分钟。如果同步等待：
- Tomcat 线程被长时间阻塞
- 用户浏览器一直 loading
- 高峰期线程池打满

引入 RabbitMQ 后：
- 用户提交任务立即返回 `taskId + "PENDING"`
- 前端轮询 `/api/task/status/{taskId}` 查询结果
- 任务状态存在 Redis（TTL 1 小时）

系统同时保留了同步接口（`/api/file/edit`、`/api/file/merge`）和异步接口（`/api/task/submit-edit`、`/api/task/submit-merge`），前端可选择。

**对应代码**：
- 同步入口：`FileController.java:61-73`
- 异步入口：`TaskController.java:24-37`

## Q17：为什么不直接用线程池 `@Async` 而要引入 RabbitMQ？

**推荐回答**：

1. **持久化**：线程池的任务在内存中，服务重启任务丢失；RabbitMQ 消息持久化到磁盘
2. **削峰**：高峰期 MQ 可以堆积消息，线程池的队列满了会拒绝任务
3. **解耦**：未来可以把 Consumer 独立部署到专门跑 AI 的机器上
4. **可观测**：RabbitMQ 管理后台可以看队列积压、消费速率，线程池缺少这些

```java
    try {

        if ("EDIT".equals(message.getType())) {
            handleEditTask(message);   // 2. 调用 Python edit
        } else if ("MERGE".equals(message.getType())) {
            handleMergeTask(message);  // 2. 调用 Python merge
        }
        updateTaskStatus(taskId, buildStatus("SUCCESS", url, saveUrl, null));  // 3. 成功
    } catch (Exception e) {
        updateTaskStatus(taskId, buildStatus("FAILED", ..., e.getMessage()));  // 4. 失败
    }
}
```

```java
        .set(idempotentKey, "1", Duration.ofHours(24));
    channel.basicAck(tag, false);
}
```

## Q28：什么是 Agent？项目中为什么需要 Agent？

**推荐回答**：

Agent = LLM + Tools + 决策循环。LLM 不再是简单地回答问题，而是能根据用户意图**自主选择调用哪个工具**来完成任务。

项目中需要 Agent 的原因是：用户输入自然语言指令（"把背景换成白色"、"把这两件衣服合成一张图"），系统需要判断：
1. 这是编辑还是合并？（单图=编辑，双图=合并）
2. 调用哪个模型？（都是 `qwen-image-edit-plus`，但参数不同）
3. 传什么参数？

如果不用 Agent，需要写大量 if-else 做意图识别和参数提取。Agent 让 LLM 来做这个决策。

## Q29：普通 LLM 调用和 Agent 有什么区别？

**推荐回答**：

| | 普通 LLM 调用 | Agent |
|---|---|---|
| 输入 | Prompt → 输出文本 | Prompt → 决策 → 调工具 → 拿结果 → 再决策... |
| 能力 | 只能生成文字 | 能执行操作（编辑图片、查数据库等） |
| 控制流 | 一次性 | 循环（ReAct 模式：Think→Act→Observe→Think...） |

项目中图片审核就是普通 LLM 调用（给图→返回"是/否"），而图片编辑走的是 Agent（给指令→LLM 决策调 `edit_image_tool`→返回结果图）。

## Q31：用户说"帮我把背景换成白色"，系统怎么知道调用哪个 Tool？

**推荐回答**：

这是 Agent 的 **Tool Choice**（工具选择）过程：

1. LLM 收到 user input 和 system_prompt、tool 描述列表
2. LLM 推理：只有一个图 → 不是合并 → 应调 `edit_image_tool`
3. LLM 输出 function call：`{name: "edit_image_tool", arguments: {image_path: "/tmp/xxx", instruction: "把背景换成白色"}}`
4. DeepAgents 框架执行该函数，拿到 `{"success": true, "url": "..."}`
5. 框架把 tool 结果返回给 LLM
6. LLM 做最终响应，输出 JSON

**核心机制**：Tool Choice 完全由 LLM 的 function calling 能力驱动。DeepAgents 底层使用 LangGraph 的 ReAct 循环，每轮 LLM 可以输出文本或 function call，框架根据输出类型决定下一步动作。

## Q32：Tool Calling 的底层原理是什么？

**推荐回答**：

底层是 OpenAI 定义的 **Function Calling 协议**。流程：

1. 请求 LLM 时，在 API 参数中传入 `tools` 列表（每个 tool 的 name、description、parameters JSON Schema）
2. LLM 返回的不是文字，而是一个 `tool_calls` 数组：`[{id, type: "function", function: {name, arguments}}]`
3. 框架解析 `tool_calls`，匹配本地注册的 Python 函数，执行并拿到结果
4. 框架把 tool 结果以 `role: "tool"` 消息追加到对话历史中
5. 再次请求 LLM，让它基于 tool 结果做最终回答

**对应代码**：
- 文件：`server.py:583-600`

```python
def invoke_agent(param: str) -> dict:
    state = deep_agent.invoke({
        "messages": [{"role": "user", "content": param}]
    })
    msg = (state or {}).get("messages") or []
    last = msg[-1] if msg else None
    content = last.content
    obj = json.loads(content)
    return obj
```

## Q38：什么是 CLIP？为什么选择 CLIP 而不是其他模型？

**推荐回答**：

CLIP（Contrastive Language-Image Pre-training）是 OpenAI 发布的多模态模型，核心能力是将**图片和文本映射到同一个 512 维语义空间**。这意味着"红色连衣裙"的文字向量和任何红色连衣裙图片的向量距离很近。

选择 CLIP 的原因：
1. **Zero-shot 能力**：不需要针对服装领域做 fine-tune，开箱即用
2. **图文对齐**：同一个向量空间同时支持图搜图和文搜图
3. **本地推理**：模型仅 ~600MB，不需要调用付费 API
4. **生态成熟**：HuggingFace Transformers 直接加载

**对应代码**：
- 模型加载：`server.py:58-74`

## Q39：图片是如何变成 512 维向量的？请结合源码说明完整流程

**推荐回答**：

**对应代码**：
- 文件：`server.py:146-175`

```python
def clip_image_to_512d(image_data: bytes) -> list:
    # 1. 加载模型（单例模式，线程安全）
    model, processor = get_clip_model_and_processor()

    # 2. 图片预处理：打开→转RGB→CLIP Processor（resize到224×224+归一化）
    img = Image.open(BytesIO(image_data)).convert("RGB")
    inputs = processor(images=img, return_tensors="pt")

    # 3. 推理（no_grad 模式，不计算梯度）
    with torch.no_grad():
        out = model.get_image_features(**inputs)
        # 兼容不同 transformers 版本的输出格式
        if hasattr(out, "pooler_output") and out.pooler_output is not None:
            image_features = out.pooler_output
        elif hasattr(out, "image_embeds") and out.image_embeds is not None:
            image_features = out.image_embeds
        else:
            image_features = out
        # 4. L2 归一化（使向量模长为1）
        image_features = image_features / image_features.norm(dim=-1, keepdim=True)

    # 5. 转为 Python list，精度压缩到6位小数
    vec = image_features[0].detach().cpu().tolist()
    return [round(float(x), 6) for x in vec]
```

**关键步骤**：L2 归一化后，两个向量的余弦相似度等于它们的点积，计算极简。

## Q40：什么是 embedding？为什么是 512 维？

**推荐回答**：

Embedding 就是用一串数字（向量）表示图片的语义。CLIP ViT-B/16 模型的设计决定了输出维度是 512——这是模型的 `projection_dim` 参数。维度越高能编码更多语义信息，但检索和存储成本也更高。512 是一个在精度和效率之间的平衡点。

**对应代码**：
- 文件：`server.py:170-171`

```python
if len(vec) != 512:
    raise ValueError(f"CLIP embedding 维度期望为 512，实际为 {len(vec)}")
```

## Q42：图搜图的相似度是怎么计算的？

**推荐回答**：

使用**余弦相似度**，但因为向量已 L2 归一化，退化为**点积**：

**对应代码**：
- 文件：`server.py:178-193`

```python
def cosine_similarity_512(a: list, b: list) -> float:
    if len(a) != 512 or len(b) != 512:
        return 0.0
    s = 0.0
    for i in range(512):
        s += float(a[i]) * float(b[i])  # 点积 = 余弦相似度（因为已归一化）
    return float(s)
```

阈值：图搜图 ≥ 0.7（较高，因为两张图片的向量比较稳定）
文搜图 ≥ 0.01（极低，因为文本相似度用字符串匹配而非 CLIP 文本编码）

## Q43：文搜图是怎么实现的？为什么不用 CLIP 的文本编码器？

**推荐回答**：

**当前实现**：用的是 `difflib.SequenceMatcher` + char 2-gram Jaccard 做**字符串相似度**，而不是 CLIP 的 `get_text_features()`。

**对应代码**：
- 文件：`server.py:217-238`

```python
def text_similarity(query: str, description: str) -> float:
    q = _normalize_text_for_similarity(query)
    d = _normalize_text_for_similarity(description)
    seq = difflib.SequenceMatcher(None, q, d).ratio()
    q2 = _char_ngrams(q, 2)  # 2-gram 字符集
    d2 = _char_ngrams(d, 2)
    jac = len(q2 & d2) / max(1, len(q2 | d2))  # Jaccard
    return float(max(seq, jac))
```

**问题**：这只做了关键词匹配——搜"红色连衣裙"，只匹配描述中有"红"和"连衣裙"文本的图片。如果图片描述写的是"crimson dress"，完全匹配不到。

**改进**：应该用 CLIP 的 `get_text_features()` 把查询文本也编码为 512 维向量，再做余弦相似度：

```python
def clip_text_to_512d(text: str) -> list:
    model, processor = get_clip_model_and_processor()
    inputs = processor(text=text, return_tensors="pt", padding=True)
    with torch.no_grad():
        text_features = model.get_text_features(**inputs)
        text_features = text_features / text_features.norm(dim=-1, keepdim=True)
    return text_features[0].detach().cpu().tolist()
```

## Q44：为什么搜索不用 MySQL？

**推荐回答**：

1. MySQL 不支持向量相似度计算，只能用 `LIKE '%红色%'` 做文本匹配——这是关键词搜索，不是语义搜索
2. 如果非要用 MySQL 做"图搜图"，需要把 512 维向量存为 512 个列，然后 `SELECT ... ORDER BY SQRT(POW(v1-q1,2)+POW(v2-q2,2)+...)` 做 KNN——每查询一次要全表扫描计算，O(n×512)，千万级数据不可接受
3. Redis 的 HNSW 索引可以做 O(log n) 的近似搜索

---

## Q45：如果图片量达到千万级，如何优化检索？

**推荐回答**：

1. **RediSearch 向量索引**：使用 Redis Stack 的 `FT.CREATE` 创建 HNSW 索引，在服务端做近似最近邻（ANN），比 Python 侧遍历快几个数量级
2. **向量数据库**：Milvus、Qdrant、Weaviate——专门为向量检索优化，支持分布式、混合搜索（向量+标量过滤）
3. **向量压缩**：512 维 → 256 维（PCA 降维）或使用乘积量化（PQ），存储和计算量减半
4. **分片策略**：按 userId 分片，用户搜索只需查自己的分片
5. **分级检索**：先粗排（ANN 召回 Top 100）→ 再精排（精确余弦相似度），平衡精度和速度

## Q46：为什么没有用 Elasticsearch / Milvus？

**推荐回答**：

当前项目是 MVP 阶段，数据量小，Redis 够用。如果要选型：

| 方案 | 优点 | 缺点 |
|------|------|------|
| Redis + RediSearch | 已有 Redis，零额外部署 | 向量检索能力不如专用库 |
| Elasticsearch 8.x | 全文搜索 + 向量搜索一体 | 资源重，运维复杂 |
| Milvus | 专业向量数据库，十亿级 | 需要额外部署和维护 |

推荐：如果只是服装图片检索（百万级），Elasticsearch 8.x 的 dense_vector + KNN 就够，且能同时做文本搜索和向量搜索的混合排序。

## Q50：大模型调用失败了怎么办？有什么降级策略？

## Q61：请介绍一下 Flash 实时对话助手的整体设计，它解决了什么问题？

**推荐回答**：

Flash 是一个「智能穿搭顾问」，用户用自然语言提问（"通勤穿什么""约会怎么搭"），系统用**打字机效果**流式返回穿搭建议。它和之前「一次性问答」的区别在于三项能力：

1. **实时流式输出（SSE）**：答案逐 token 推送，不用等整段生成完，体验好。
2. **RAG 检索增强**：回答前先从服装搭配知识库（色彩/风格/体型/场合 4 篇 md）检索相关知识，注入 prompt，回答更专业、可溯源。
3. **长短期记忆**：长期记「用户是谁」（风格/颜色/体型偏好），短期记「聊了什么」（当前会话摘要），多轮对话不「失忆」。

**整体链路**：

```
前端 FlashView ──fetch 流式──▶ Java FlashController ──SseEmitter 透传──▶ Python /api/chat
                                   │ 查 user_profile（长期画像）          │ 短期记忆(Redis) + RAG(ChromaDB)
                                   └────────────────────────────────────▶ 拼画像 + 知识 + 记忆 ─▶ 流式生成
```

- 前端：`loomai-fronted/src/views/FlashView.vue`、`loomai-fronted/src/services/api.js`
- Java：`controller/FlashController.java`、`service/impl/FlashServiceImpl.java`
- Python：`loomai-agent/server.py` 的 `chat_api()`、`rag.py`、`memory.py`

## Q62：为什么实时对话用 SSE 而不是 WebSocket 或轮询？

**推荐回答**：

三种实时方案的对比：

| 方案 | 方向 | 连接 | 适用场景 |
|------|------|------|---------|
| 轮询 | 客户端→服务端（主动拉） | 每次新建/复用 | 低频、实时性要求不高 |
| WebSocket | 双向全双工 | 长连接 + 升级协议 | 聊天室、协作编辑、服务端主动推送 |
| SSE | 服务端→客户端（单向推） | 长连接（HTTP） | 单向流式推送（AI 生成、日志、通知） |

Flash 是「问一句答一句」的**单向流**，WebSocket 过重（握手、心跳、帧管理都更复杂），轮询延迟高且空耗资源。SSE 基于 HTTP、实现简单、浏览器自动重连，天然契合「打字机」式流式输出。

**关键取舍**：SSE 只能服务端→客户端单向推送，客户端发消息还是走普通的 `POST` 请求——Flash 恰好是「请求走 POST、响应走 SSE」，两者结合刚好覆盖双向需求。

## Q63：前端为什么不用 `EventSource` 而用 `fetch + ReadableStream` 手动解析 SSE？

**推荐回答**：

因为 **`EventSource` 只能发 GET 请求，且不能自定义请求头**，而 Flash 接口需要 `Authorization: Bearer <JWT>` 鉴权。所以前端用 `fetch` 携带 Authorization 头，拿到 `response.body`（ReadableStream）后手动解析 SSE 文本。

**对应代码**：`loomai-fronted/src/services/api.js`

```javascript
export async function flashChat({ message, sessionId }) {
  const auth = useAuthStore()
  const res = await fetch('/api/flash/chat', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      Authorization: `Bearer ${auth.token}`,
    },
    body: JSON.stringify({ message, sessionId }),
  })
  if (!res.ok || !res.body) throw new Error(`请求失败（${res.status}）`)
  return res.body   // 返回 ReadableStream，由调用方逐段读取
}
```

**对应代码**：`FlashView.vue` 的 `handleSend()` 里手动解析：

```javascript
const reader = stream.getReader()
const decoder = new TextDecoder()
let buffer = ''
while (true) {
  const { done, value } = await reader.read()
  if (done) break
  buffer += decoder.decode(value, { stream: true })   // stream:true 处理中文被分片截断
  let idx
  while ((idx = buffer.indexOf('\n\n')) !== -1) {      // SSE 事件用空行分隔
    const rawEvent = buffer.slice(0, idx)
    buffer = buffer.slice(idx + 2)
    handleSseEvent(rawEvent, assistantMsg)             // 解析 data:{...}，追加 delta
  }
}
```

**面试官继续追问**：手动解析 SSE 有哪些要注意的点？

**深入回答**：
1. **事件边界**：`reader.read()` 每次返回的 chunk 不一定对齐事件边界，必须用 buffer 累积 + 按 `\n\n` 切分，残留部分留待下一轮。
2. **中文乱码**：多字节字符可能被 TCP 分片截断，`TextDecoder({ stream: true })` 让解码器记住未完成字节序列。
3. **半包/粘包**：本质和 TCP 拆包粘包一样，SSE 的 `\n\n` 就是「定界符」。

## Q64：Java 端如何实现 SSE？`SseEmitter` 的原理是什么？

**推荐回答**：

Spring MVC 用 `SseEmitter` 抽象服务端推送。Controller 返回 `SseEmitter` 对象而不是普通 `Result`，Spring 会把它和当前请求绑定，之后调用 `emitter.send()` 时，Spring 把数据序列化成 SSE 格式（`data: {...}\n\n`）推给客户端。

**对应代码**：`FlashController.java`

```java
@PostMapping("/chat")
public SseEmitter chat(@RequestHeader("Authorization") String authorization,
                       @RequestBody @Validated FlashChatRequest request) {
    Long userId = jwtUtil.getUserId(jwtUtil.parseToken(authorization));
    SseEmitter emitter = new SseEmitter(300_000L);   // 5 分钟超时
    // 异步处理，避免阻塞 Tomcat 线程
    CompletableFuture.runAsync(() ->
            flashService.streamChat(emitter, userId, request.getSessionId(), request.getMessage()));
    return emitter;   // 立即返回，Tomcat 线程不阻塞
}
```

**面试官继续追问**：为什么用 `CompletableFuture.runAsync` 包一层？

**深入回答**：如果 Controller 方法里同步执行 `streamChat`，Tomcat 工作线程会被占用整个流式期间（最长 5 分钟），并发一高线程池就打满。`runAsync` 把耗时逻辑丢到 `ForkJoinPool.commonPool()`，Controller 立即返回 emitter，Tomcat 线程释放。但注意 commonPool 线程数有限（CPU 核数-1），生产环境应注入自定义线程池。

**`SseEmitter(300_000L)` 超时机制**：超时会抛 `AsyncRequestTimeoutException`，连接被强制断开，流被截断。

## Q65：Java 如何把 Python 的流式结果透传给前端？`BodyHandlers.ofLines()` 是什么？

**推荐回答**：

Java 端不直接调大模型，而是用 JDK 17 内置 `HttpClient` 调 Python 的 `/api/chat`，再把 Python 吐出的 SSE 逐条解析、重新用 `SseEmitter` 转推给前端。

**对应代码**：`FlashServiceImpl.java`

```java
// 关键：BodyHandlers.ofLines() 把响应体当「行流」返回，来一行处理一行，而非等整个响应读完
HttpResponse<Stream<String>> response =
        httpClient.send(request, HttpResponse.BodyHandlers.ofLines());

try (Stream<String> lines = response.body()) {
    Iterator<String> it = lines.iterator();
    while (it.hasNext()) {
        String line = it.next();
        if (line == null || !line.startsWith("data:")) continue;
        String payload = line.substring("data:".length()).trim();
        if (payload.isEmpty()) continue;
        if ("[DONE]".equals(payload)) break;          // 结束标记
        JsonNode node = objectMapper.readTree(payload);
        String delta = node.path("delta").asText("");
        if (!delta.isEmpty()) {
            emitter.send(Map.of("delta", delta));      // 重新序列化成 SSE 转推
        }
    }
}
emitter.complete();
```

**面试官继续追问**：`ofLines()` 和 `ofString()` 的区别？

**深入回答**：`ofString()` 会把整个响应体读成一个完整 String 才返回（一次性）；`ofLines()` 返回 `Stream<String>`，按行惰性消费，配合 `Iterator` 可以「来一行处理一行」。流式转发必须用 `ofLines()`，否则 Java 会卡到 Python 全部生成完才继续，前端又变成「一次性输出」。

**追问二**：三层链路为什么每层都要「解析再重发」？

**深入回答**：Python 吐 `data: {"delta":"你"}` → Java 解析出 delta → 重新 `emitter.send(Map.of("delta", delta))` → Spring 再序列化成 SSE。三层格式保持一致，但存在多次无意义的序列化/反序列化。优化方向是 Java 直接把 Python 的原始 SSE 字节流透传（不解析不重打包），前端解析一次即可。

## Q66：Python 端如何做流式生成？为什么绕过了 `ChatTongyi.stream()`？

**推荐回答**：

最初用 LangChain 的 `llm.stream()`（`ChatTongyi`），但**前端始终一次性收到整段回答**。排查发现根因在 Python：`langchain-community` 的 `ChatTongyi._stream()` 把 DashScope 增量响应转成 LangChain 的 `ChatMessageChunk` 时，调用了 `convert_dict_to_message(is_chunk=True)`，**把增量 token 弄丢了**——每个 chunk 的 `.content` 都是空字符串，最后只 yield 一个整段文本 chunk。

**解决办法**：绕过 LangChain，直接调 DashScope 底层 SDK，用 `incremental_output=True` 拿到增量 token：

**对应代码**：`server.py` 的 `generate()`

```python
responses = Generation.call(
    model="qwen-plus",
    messages=dashscope_messages,
    result_format="message",
    temperature=0.1,
    stream=True,
    incremental_output=True,   # 每个响应只含「新增的一个 token」，而非累积全文
    api_key=API_KEY,
)
for resp in responses:
    choices = resp.get("output", {}).get("choices") or []
    if not choices:
        continue
    token = choices[0].get("message", {}).get("content", "") or ""
    if token:
        ai_parts.append(token)
        yield f"data: {json.dumps({'delta': token}, ensure_ascii=False)}\n\n"
```

**面试官继续追问**：`incremental_output=True` 和默认的流式有什么区别？

**深入回答**：默认流式（`incremental_output=False`）每次返回**从头累积的完整文本**（第 N 次返回前 N 个 token 拼接），前端如果直接追加会重复；`incremental_output=True` 每次只返回**新增的那一个 token**，前端直接追加即可，形成打字机效果。这是排查「前端非流式」问题时定位到的关键差异。

## Q67：什么是 RAG？为什么需要 RAG？它和微调（Fine-tuning）有什么区别？

**推荐回答**：

**RAG（Retrieval-Augmented Generation，检索增强生成）**：在生成回答前，先从外部知识库检索最相关的片段，塞进 prompt，让模型「照着资料回答」。

**为什么需要 RAG**：
1. 大模型的通用知识可能过时、太泛，缺少项目特定的搭配规则。
2. 无法溯源——回答「看起来对」但不知道依据。
3. 易幻觉——没有外部约束时可能编造不存在的理论。

**RAG vs 微调**：

| 维度 | RAG | 微调 |
|------|-----|------|
| 原理 | 检索外部知识注入 prompt | 用领域数据继续训练模型权重 |
| 知识更新 | 改知识库即可，实时生效 | 需重新训练 |
| 成本 | 低（只花检索 + 推理 token） | 高（GPU 训练） |
| 可解释性 | 强（能指出引用了哪段） | 弱（权重黑盒） |
| 适用 | 知识频繁更新、需要溯源 | 改变模型风格/格式/行为 |

本项目是「学生演示项目 + 知识库小且稳定」，RAG 是更合适的选择。

## Q68：RAG 的完整流程是怎样的？请结合项目源码说明

**推荐回答**：

RAG 分**离线入库**和**在线检索**两个阶段。

**① 离线入库**（`rag.py` 的 `ingest_structured()`）：按 Markdown 标题层级切块 → 打 metadata → 向量化 → 存入 ChromaDB。

```python
def ingest_structured() -> int:
    collection = get_collection()
    existing = collection.get()
    if existing.get("ids"):
        collection.delete(ids=existing["ids"])   # 清空旧数据，避免新旧 chunk 混合
    documents, ids, metadatas = [], [], []
    for fname in sorted(os.listdir(KNOWLEDGE_DIR)):
        if not fname.endswith(".md"):
            continue
        content = open(os.path.join(KNOWLEDGE_DIR, fname), encoding="utf-8").read()
        for i, (chunk, meta) in enumerate(_split_markdown(content, fname)):
            documents.append(chunk)
            ids.append(f"{fname}-{i}")
            metadatas.append(meta)                # {document, parent_category, category}
    collection.upsert(documents=documents, ids=ids, metadatas=metadatas)
    return len(documents)
```

**② 在线检索**（`rag.py` 的 `retrieve_advanced()` + `server.py` 组装 prompt）：完整管线 = Query 改写 → 混合召回（向量 + BM25）→ 相似度阈值 → RRF 融合 → Rerank。

```python
def retrieve_advanced(query: str, history: str = "", top_k: int = RERANK_TOP_K):
    q = rewrite_query(query, history)                       # ① LLM 改写
    vector_hits = _vector_retrieve_with_scores(q, top_k=20) # ② 向量召回
    bm25_hits = bm25_retrieve(q, top_k=20)                  # ② BM25 召回
    vector_hits = _apply_threshold(vector_hits)             # ④ 阈值 0.70（只作用于向量）
    fused = _rrf_fusion([vector_hits, bm25_hits])           # ③ RRF 融合
    if not fused:
        return []                                           # 无相关 Context，不硬凑
    candidates = [text for _, text, _ in fused]
    return rerank(q, candidates, top_n=top_k)               # ⑤ Rerank → Top 5
```

```python
# server.py 中把检索结果拼进 system prompt
knowledge = retrieve_advanced(message, history, top_k=5)
knowledge_text = "\n".join(f"- {k}" for k in knowledge if k)
```

- 入库：`rag.py:161-181`（`ingest_structured()`）

## Q69：为什么用 ChromaDB？向量数据库怎么选型？

**推荐回答**：

**ChromaDB** 是嵌入式向量数据库，Python 一行启动、自带持久化、自带 embedding function 抽象，适合「本地单机、知识库几百条」的规模。

| 方案 | 类型 | 优点 | 缺点 |
|------|------|------|------|
| ChromaDB | 嵌入式 | 零部署、持久化、LangChain 集成好 | 单机、数据量大性能一般 |
| FAISS | 算法库 | 检索极快、GPU 友好 | 无持久化、无元数据管理，要自己搭 CRUD |
| Milvus / Qdrant / Pinecone | 分布式向量库 | 十亿级、混合搜索 | 需单独部署、运维成本高 |

本项目知识库只有 4 篇文档、几十个片段，ChromaDB 完全够用。若数据量到千万级，迁移到 Milvus 或 Qdrant 做分布式 ANN 检索。

## Q70：embedding 模型用的是什么？`text-embedding-v3` 有什么特点？

**推荐回答**：

用的是 DashScope 的 `text-embedding-v3`，输出 **1024 维**向量。

**对应代码**：`rag.py` 的 `DashScopeEmbeddingFunction`

```python
class DashScopeEmbeddingFunction(chromadb.EmbeddingFunction):
    def __init__(self, model: str = "text-embedding-v3"):
        self.model = model

    def name(self) -> str:
        return "dashscope-text-embedding-v3"

    def __call__(self, input):
        if isinstance(input, str):
            input = [input]
        embeddings = []
        for text in input:
            resp = TextEmbedding.call(model=self.model, input=text, api_key=API_KEY)
            if resp.status_code == 200:
                embeddings.append(resp.output["embeddings"][0]["embedding"])
            else:
                embeddings.append([0.0] * 1024)   # 降级：零向量
        return embeddings
```

**关键点**：
1. **继承 `chromadb.EmbeddingFunction`**：基类把 `embed_query()` 委托给 `__call__()`，只实现 `__call__` 就能同时支持入库（`upsert`）和检索（`query`）。
2. **1024 维**：维度越高表达力越强，但存储和计算开销越大。相比 CLIP 的 512 维（图片），文本用 1024 维语义更细。
3. **单条失败降级为零向量**：零向量在余弦空间里和任何向量相似度≈0，不会被检索到，不会「污染」Top-K，只是少了这条知识。

## Q71：知识库是怎么切块的？为什么按 Markdown 标题层级切分？

**推荐回答**：

当前用 `_split_markdown()` 按 **Markdown 标题层级结构化切分**：解析 `#`（一级标题）为 `parent_category`、`##`（二级标题）为 `category`，以 `##` 为边界切 chunk（标题 + 正文一起保留），并为每条 chunk 打上 metadata。超过 512 字符的长 chunk 再由 `_split_long_chunk()` 二次切分。

```python
def _split_markdown(content: str, fname: str):
    """按 Markdown 标题层级切分：解析 # 为 parent_category、## 为 category，
    以 ## 为边界切 chunk（标题 + 正文一起保留），过长再二次切分。"""
    lines = content.split("\n")
    parent_category = ""
    results = []
    current_category = ""
    buf = []

    def flush():
        if not current_category or not buf:
            return
        text = "\n".join(buf).strip()
        if not text:
            return
        meta = {"document": fname,
                "parent_category": parent_category,
                "category": current_category}
        for sub in _split_long_chunk(text):   # 过长二次切分（512 字符）
            results.append((sub, meta))

    for line in lines:
        stripped = line.strip()
        if stripped.startswith("## "):
            flush()
            current_category = stripped[3:].strip()
            buf = [stripped]
        elif stripped.startswith("# "):
            parent_category = stripped[2:].strip()
        elif current_category and stripped:
            buf.append(stripped)

    flush()
    return results
```

**为什么按标题层级而不是固定 token 长度**：
1. 知识库本身是结构化 Markdown（`#` 一级 / `##` 二级），按标题切能天然对齐「章节」边界——一个 `##` 小节就是一个语义完整的 chunk，标题 + 正文一起保留，检索到的片段自带「这是哪一章哪一节」的 context。
2. 固定 token 切块（如 512 + overlap 64）是通用方案，但会**无视文档结构**——可能在句子中间、甚至在标题里硬切。

**代价**：粒度不如固定 token 可控（某章节可能特别长），所以用 `_split_long_chunk()` 对超 512 字符的长 chunk 二次切分兜底。

**对应代码**：`rag.py:121-158`（`_split_markdown`）、`rag.py:111-118`（`_split_long_chunk`）

## Q72：检索出来的知识是怎么注入 prompt 的？最终取几条？阈值怎么定？

**推荐回答**：

检索结果以「列表」形式拼进 system prompt，用自然语言告诉模型「这些是参考资料」：

```python
system_prompt = (
    "你是「Flash」，一位专业的服装搭配助手。请用自然亲切的语气，给出具体、可执行的穿搭建议。"
    "只做文字交流，不涉及图片。回答简洁，避免过度展开。"

    context_parts.append(f"可参考的搭配知识：\n{knowledge_text}")  # - 片段1 \n - 片段2 ...

```

**最终取几条**：`RERANK_TOP_K=5`（Rerank 后返回 Top 3~5）。但注意这不是「裸 top_k」——最终条数由 Rerank 决定，且前面有相似度阈值把关：

| 参数 | 值 | 作用 |
|------|-----|------|
| `VECTOR_TOP_K` | 20 | 向量召回候选数（宽召回） |
| `BM25_TOP_K` | 20 | BM25 召回候选数 |
| `SIMILARITY_THRESHOLD` | 0.70 | 余弦相似度阈值（过滤无关向量候选） |
| `RERANK_TOP_K` | 5 | Rerank 后最终注入条数 |

**阈值 0.70 怎么定**：经验初值。调高（如 0.8）过滤更多「勉强相关」知识，回答更保守；调低（如 0.6）放进更多候选，可能引入噪声。理想做法是拿「问题-正确知识」标注集在验证集上扫阈值。

**面试官继续追问**：直接拿用户原话去检索，有什么局限？怎么解决？

**深入回答**：用户口语化提问（"我下周去参加婚礼穿啥"）和知识库书面表述（"正式场合建议深色西装"）存在**语义鸿沟**。本项目已用 **Query 改写**解决：`rewrite_query()` 用 `qwen-plus`（`temperature=0.0`）把多轮追问（结合对话摘要）改写成语义完整、可独立检索的 query 再检索。

## Q73：RAG 会引入幻觉吗？怎么缓解？

**推荐回答**：

RAG 只能**降低**幻觉概率，不能根除。即使检索到正确知识，模型仍可能无视检索结果或曲解知识片段。

**缓解手段**：
1. **明确指令**：prompt 里写「只依据给定资料回答，资料没有就明说不知道」。
2. **引用标注**：要求模型在回答中标注引用来源（本项目 metadatas 已存 `document` / `parent_category` / `category`，可溯源到具体章节）。
3. **相似度阈值**（✅ 已实现）：`SIMILARITY_THRESHOLD=0.70` 丢弃低相关向量候选，且 RRF 融合结果为空时直接返回 `[]`，不拿无关知识「硬凑」。
4. **重排序 Rerank**（✅ 已实现）：用 Cross-Encoder（`bge-reranker-base`）对召回结果二次精排，把最相关的放最前。
5. **答案校验**：生成后再用模型或规则校验回答是否与资料一致（未实现，进阶方向）。

## Q74：Query 改写（Query Rewrite）是做什么的？为什么只在有多轮历史时才改写？

**推荐回答**：

Query 改写是用一次小 LLM 调用，把用户「口语化、依赖上下文」的提问改写成「语义完整、适合向量检索」的标准 query，缩小口语与知识库书面表述之间的**语义鸿沟**。

```python
def rewrite_query(query: str, history: str = "") -> str:
    if not history:
        return query          # 首轮无历史，直接返回原 query
    try:
        from dashscope import Generation
        prompt = (
            "你是检索查询改写助手。请把用户的问题改写成一句适合向量检索的、"
            "独立且完整的中文查询。要求：只改写查询本身，不回答问题；"
            "保留用户真实意图；保留关键场景和限制条件；去掉无意义口语；"
            "不得凭空添加事实。只输出改写后的查询。\n"
            f"对话历史：{history}\n"
            f"当前问题：{query}\n"
            "改写后的查询："
        )
        resp = Generation.call(
            model="qwen-plus",
            messages=[{"role": "user", "content": prompt}],
            result_format="message",
            temperature=0.0,      # 确定性任务，温度最低
            api_key=API_KEY,
        )
        if resp.status_code == 200:
            content = resp.output["choices"][0]["message"]["content"].strip()
            if content:
                return content
    except Exception as e:
        print(f"Query 改写失败，使用原查询: {e}")
    return query                    # 失败降级：返回原 query
```

**为什么只在有历史时改写**：
1. 首轮问题通常是完整句子（"通勤穿什么"），本身就能检索，无需改写。
2. 多轮追问（"那配什么鞋"）依赖上文——"那"指代什么、"鞋"配什么场合，只有结合对话摘要才能补全成语义完整的 query。

**为什么 `temperature=0.0`**：改写是「确定性」任务，温度最低保证输出稳定、可复现，不会「越改越离谱」。

**对应代码**：`rag.py:185-213`（`rewrite_query()`）

**面试官继续追问**：改写失败或改写歪了怎么办？

**深入回答**：失败（API 异常、返回空）直接返回原 query，不影响后续检索；prompt 里显式约束「不得凭空添加事实」，避免改写时编造信息。

## Q75：为什么要「混合召回」（向量 + BM25）？两者各自擅长什么？

**推荐回答**：

向量（Dense）和 BM25（Sparse）是互补的两种召回方式：

| 方式 | 匹配原理 | 擅长 | 盲区 |
|------|---------|------|------|
| 向量检索 | 语义相似（embedding 余弦） | 近义但用词不同（"西装"↔"正装"） | 专有名词/数字/颜色等长尾词 |
| BM25 | 词法匹配（词频加权） | 精确命中关键词（"莫兰迪色系""梨形身材"） | 同义改写、语义相近 |

**只用向量会漏什么**：向量可能「泛化过头」，对低频但关键的词（颜色、数字、专有名词）召回不准。BM25 正好补上精确的词法匹配。

```python
def bm25_retrieve(query: str, top_k: int = BM25_TOP_K):  # BM25_TOP_K=20
    try:
        import jieba
        from rank_bm25 import BM25Okapi
    except ImportError:
        return []               # 未装依赖则跳过 BM25，退化为纯向量检索
    corpus = _all_chunks()
    tokenized_corpus = [jieba.lcut(text) for _, text in corpus]   # 中文必须分词
    bm25 = BM25Okapi(tokenized_corpus)
    scores = bm25.get_scores(jieba.lcut(query))
    ranked = sorted(range(len(corpus)), key=lambda i: scores[i], reverse=True)[:top_k]
    return [(corpus[i][0], corpus[i][1], float(scores[i])) for i in ranked if scores[i] > 0]
```

两路各召回 Top 20，再交给 RRF 融合（见 Q76）。

**对应代码**：`rag.py:217-227`（向量召回）、`rag.py:240-254`（BM25 召回）

**面试官继续追问**：BM25 为什么用 `jieba` 分词？

**深入回答**：BM25 按空格分词，中文不分词会把整句当一词，完全失效。所以先用 `jieba.lcut()` 把中文切成语义词再喂给 `BM25Okapi`。

## Q76：RRF 融合的原理是什么？为什么不直接把两路分数相加？

**推荐回答**：

RRF（Reciprocal Rank Fusion，倒数排名融合）把多个召回排序结果**按排名**加权合并，而不是按原始分数：

```python
def _rrf_fusion(ranked_lists, k: int = RRF_K):  # RRF_K=60
    score = {}
    text_by_id = {}
    for ranked in ranked_lists:
        for rank, item in enumerate(ranked):
            doc_id, text = item[0], item[1]
            score[doc_id] = score.get(doc_id, 0.0) + 1.0 / (k + rank + 1)
            text_by_id[doc_id] = text
    return sorted(
        [(doc_id, text_by_id[doc_id], s) for doc_id, s in score.items()],
        key=lambda x: x[2], reverse=True)
```

**为什么不直接相加分数**：向量相似度（0~1）和 BM25 分数（无上界的词频加权）**量纲完全不同**，直接相加会让 BM25 的高分项「碾压」向量分。RRF 只关心**排名**、忽略原始分数，天然解决「不同检索器分数不可比」的问题。

**`k=60` 的作用**：平滑常数，防止排名靠前的文档权重过大（`1/(60+0+1)` 和 `1/(60+1+1)` 差距很小，符合「排名相邻权重接近」的直觉）。既在向量路又在 BM25 路都排名靠前的文档，RRF 分数最高，被推到融合结果顶部。

**对应代码**：`rag.py:258-271`（`_rrf_fusion()`）

## Q77：相似度阈值 0.70 是怎么定的？为什么只作用于向量召回？

**推荐回答**：

```python
SIMILARITY_THRESHOLD = 0.70   # 余弦相似度阈值

def _apply_threshold(vector_hits, threshold: float = SIMILARITY_THRESHOLD):
    """丢弃余弦相似度 < threshold 的向量结果，只保留语义足够相关的候选。"""
    return [(i, t, s) for (i, t, s) in vector_hits if s >= threshold]
```

**作用**：丢弃语义上「其实不太相关」的向量候选，避免把无关知识硬塞进 prompt 误导模型。

**为什么只作用于向量召回**：BM25 分数是词法相关度，和余弦相似度**不在一个量纲**，不能共用同一阈值。所以阈值过滤只在 Dense 向量结果上做、在 RRF 融合**之前**完成。

**阈值怎么定**：0.70 是经验初值，需实测调优。调高（0.8）过滤更多「勉强相关」知识，回答更保守、更依赖模型自身知识；调低（0.6）放进更多候选，可能引入噪声。理想做法是拿「问题-正确知识」标注数据在验证集上扫阈值，找召回率和噪声的平衡点。

**兜底**：RRF 融合结果为空时 `retrieve_advanced` 直接返回 `[]`，不强行注入无关知识（宁缺毋滥）。

**对应代码**：`rag.py:104`（常量）、`rag.py:275-277`（`_apply_threshold()`）

## Q78：Cross-Encoder 和 Bi-Encoder 有什么区别？Rerank 为什么用 Cross-Encoder？

**推荐回答**：

| 维度 | Bi-Encoder | Cross-Encoder |
|------|-----------|---------------|
| 编码方式 | query 和 doc **各自独立**编码成向量 | `[query, doc]` **拼接**一起过模型 |
| 交互 | 无（只比余弦） | 有（attention 让 query/doc 每个 token 交互） |
| 速度 | 快 | 慢 |
| 精度 | 粗 | 准 |
| 用途 | 全库召回（`text-embedding-v3`） | 少量候选精排（`bge-reranker-base`） |

本项目前面的向量检索是 Bi-Encoder（`text-embedding-v3`），快但「query 和文档没有交互」；Rerank 阶段用 Cross-Encoder（`bge-reranker-base`）把 `[query, doc]` 拼成 pair 一起过 Transformer，精确建模两者交互，相关性判断更准。

```python
_reranker = None

def _get_reranker():
    global _reranker
    if _reranker is None:           # 懒加载：首次调用才下载/加载权重
        from FlagEmbedding import FlagReranker
        import torch
        _reranker = FlagReranker(RERANK_MODEL, use_fp16=torch.cuda.is_available())
    return _reranker

def rerank(query: str, documents, top_n: int = RERANK_TOP_K):  # RERANK_TOP_K=5
    if not documents:
        return []
    if len(documents) <= 1:
        return documents
    try:
        reranker = _get_reranker()
        pairs = [[query, doc] for doc in documents]
        scores = reranker.compute_score(pairs, normalize=True)   # 归一化到 0~1
        ranked = sorted(zip(documents, scores), key=lambda x: x[1], reverse=True)
        return [doc for doc, _ in ranked[:top_n]]
    except Exception as e:
        print(f"Rerank 失败，回退原顺序: {e}")
        return list(documents)[:top_n]   # 失败回退 RRF 顺序
```

**为什么不对全库做 Rerank**：Cross-Encoder 慢，只能对融合后的少量候选（几十条）做精排，不能对全库（几百条）逐个算。所以工程上是「先 Bi-Encoder 宽召回、后 Cross-Encoder 精排」的标准范式。

**`use_fp16=torch.cuda.is_available()`**：有 GPU 用 fp16 加速，无 GPU（CPU-only）用 fp32。

**对应代码**：`rag.py:107`（`RERANK_MODEL`）、`rag.py:284-309`（`_get_reranker()` + `rerank()`）

## Q79：这个 RAG 管线每一步都可能失败，怎么保证对话不中断？

**推荐回答**：

全链路都做了**降级**，任何一步挂了都不影响流式生成，只是「这次回答没有知识增强」：

| 环节 | 失败场景 | 降级行为 |
|------|---------|---------|
| Query 改写 | API 异常 / 返回空 | 返回原 query（`rewrite_query` 的 `except` + 末尾 `return query`） |
| BM25 召回 | 未装 `jieba`/`rank_bm25` | `ImportError` → 返回 `[]`，退化为纯向量检索 |
| Rerank | 模型加载失败 / 推理异常 | 回退 RRF 顺序取 top_n（`except` → `list(documents)[:top_n]`） |
| 整条管线 | embedding API 超时等 | 最外层 `try/except` 包住 `retrieve_advanced`，捕获后 `knowledge_text=""` |

```python
# server.py 中
knowledge_text = ""
try:
    knowledge = retrieve_advanced(message, history, top_k=5)
    knowledge_text = "\n".join(f"- {k}" for k in knowledge if k)
except Exception as e:
    print(f"RAG 检索失败: {e}")   # 检索失败不阻断对话，降级为纯生成
```

**设计原则**：可用性优先。RAG 是「增强」不是「必需」——检索挂了，模型依然能用自身知识回答。宁可少一段知识增强，也不能让整个对话 500。

**对应代码**：`rag.py:185-213`、`rag.py:240-254`、`rag.py:295-309`、`server.py:693-699`

## Q80：升级后的 RAG 多了 Query 改写 + Rerank 两次额外调用，延迟和成本怎么控制？

**推荐回答**：

先分解新增延迟：

| 新增环节 | 类型 | 延迟量级 | 控制手段 |
|---------|------|---------|---------|
| Query 改写 | 1 次 LLM 调用（qwen-plus） | ~百 ms 级 | 只在有历史时触发；首轮直接跳过 |
| BM25 召回 | 本地计算 | ~ms 级 | 无额外成本 |
| Rerank | 本地模型推理（CPU） | ~百 ms 级 | 懒加载（首轮加载一次）、只对少量候选 |

**关键控制点**：
1. **Query 改写按需触发**：`if not history: return query`，首轮零额外 LLM 调用。
2. **Rerank 懒加载 + 局部精排**：模型首次调用才加载（之后走缓存），且只对 RRF 融合后的几十条候选精排，不对全库。
3. **阈值提前过滤**：`_apply_threshold` 在融合前砍掉低相关候选，减少后续 Rerank 的 pair 数量。

**成本角度**：相比「回答生成」的那次 qwen-plus 调用，Query 改写的 token 很少（只有改写 prompt + 一句 query）；BM25/Rerank 是本地计算，不产生 API 费用。

**面试官继续追问**：还能怎么进一步优化延迟？

**深入回答**：
1. Query 改写用更便宜的小模型（qwen-turbo）或缓存常见改写结果。
2. Rerank 模型量化（INT8）或换更小的 reranker，推理更快。
3. 若知识库增长，向量召回改用 HNSW 索引（ChromaDB 已内置），把 ANN 查询从 O(n) 降到 O(log n)。
4. 整条管线可并行化：Query 改写与「先用原 query 做向量召回」并行，改写完成后只补 BM25 路。

## Q82：短期记忆为什么用「摘要式」而不是「窗口式」？`ConversationSummaryMemory` 的原理？

**推荐回答**：

**窗口式记忆**保留最近 N 轮**原始对话**，信息无损但 token 消耗随轮数线性增长，且超过窗口就彻底丢失早期信息。

**摘要式记忆**每轮对话后用 LLM 把历史**压缩成一段摘要**（`memory.buffer`），注入 prompt 的始终是固定长度摘要——聊 100 轮，上下文不膨胀。

**对应代码**：`memory.py`

```python
from langchain_classic.memory import ConversationSummaryMemory

class ChatMemoryStore:
    def load_memory(self, session_id: str) -> ConversationSummaryMemory:
        memory = ConversationSummaryMemory(llm=self.llm, memory_key="chat_history")
        saved = self.redis.get(f"chat:session:{session_id}:summary")
        if saved:
            memory.buffer = saved   # 把上次摘要装回 buffer
        return memory

    def save_turn(self, session_id, memory, user_msg, ai_msg):
        memory.save_context({"input": user_msg}, {"output": ai_msg})  # 触发 LLM 重新摘要
        summary = getattr(memory, "buffer", "")
        if summary:
            self.redis.set(f"chat:session:{session_id}:summary", summary, ex=7200)  # TTL 2h
```

**面试官继续追问**：摘要式记忆的代价是什么？

**深入回答**：
1. **每次对话额外调一次 LLM**（`save_context` 内部触发 summarize），一轮对话实际调了两次模型——一次生成回答、一次更新摘要，增加了延迟和 API 成本。
2. **摘要丢失细节**：用户说「我 175cm 80kg」，摘要可能只写「用户偏壮」，数字信息被压缩丢失。

**改进**：摘要式 + 窗口式混合——关键实体（身高体重、具体颜色）用结构化字段单独存，对话流水用摘要压缩。

## Q84：流式输出和记忆保存有什么矛盾？当前实现怎么处理？

**推荐回答**：

**矛盾**：流式输出只有**增量 token**，而记忆保存需要**这一轮的完整回答文本**（作为 `ai_msg`）。所以必须「边流边攒」，把每个 token 拼起来。

**当前实现**（`server.py` 的 `generate()`）：

```python
ai_parts = []
for resp in responses:
    token = choices[0].get("message", {}).get("content", "") or ""
    if token:
        ai_parts.append(token)   # 边流边攒
        yield f"data: {json.dumps({'delta': token})}\n\n"
ai_text = "".join(ai_parts)       # 生成完拼出全文
memory_store.save_turn(session_id, memory, message, ai_text)  # 再保存记忆
```

**取舍**：`save_turn` 在所有 token 生成**之后**才执行，不会阻塞流式输出。代价是：如果生成中途进程 crash 或网络断开，`save_turn` 没执行，这一轮对话就丢了（记忆没更新）。

**改进**：流式期间同步攒 `ai_parts`，每攒满一定长度就落盘（写 Redis 临时 buffer），崩溃后下次能部分恢复。

## Q85：Flash 这条链路有哪些可靠性问题？怎么优化？

**推荐回答**：

1. **SSE 三层透传，故障点多**：前端→Java→Python 任意一层断了都中断流，且**没有自动重连和断点续传**。
   → 前端 `onerror` 携带 `Last-Event-ID` 重连；Java 对 Python 瞬时故障做重试。

2. **「先流后存」丢记忆**：生成中途崩溃，本轮对话不进摘要。
   → 边流边落盘（见 Q84）。

3. **摘要记忆丢细节**：LLM 压缩掉具体数字/颜色。
   → 摘要式 + 结构化字段混合。

4. ~~RAG 检索无相似度阈值~~【已解决】：现 `SIMILARITY_THRESHOLD=0.70` 过滤低相关向量候选，且 RRF 融合为空时返回 `[]`，不「硬凑」无关知识。

5. ~~知识库切块过于简单~~【已解决】：改用 `_split_markdown` 按 Markdown 标题层级结构化切分（`#`→`parent_category`、`##`→`category`），超 512 字符由 `_split_long_chunk` 二次切分。

6. **长期画像「先查后写」有并发竞态**：两个请求同时查到 null 都 insert，触发唯一键冲突。
   → 数据库 `INSERT ... ON DUPLICATE KEY UPDATE`。

7. **前端 localStorage 记忆不跨设备、不落库**：换设备、清缓存就丢。
   → 会话历史落库（MySQL/Redis），前端只做展示。

## Q86：如果让你把 Flash 的 RAG 升级到生产级，你会怎么做？

**推荐回答**：

当前已从 Naive RAG 升级为「Query 改写 → 混合召回（向量+BM25）→ 阈值 0.70 → RRF → Cross-Encoder Rerank」的完整管线，**已落地**：

1. **查询优化**：`rewrite_query()` 用 `qwen-plus`（`temperature=0.0`）改写多轮追问。
2. **召回优化**：向量（`text-embedding-v3`）+ BM25（`jieba` + `BM25Okapi`）**混合召回**，各取 Top 20。
3. **重排序**：Cross-Encoder `bge-reranker-base` 对融合候选二次精排。
4. **切块优化**：`_split_markdown` 按 Markdown 标题层级结构化切分 + metadata。
5. **阈值过滤**：`SIMILARITY_THRESHOLD=0.70` 丢弃低相关候选，RRF 融合为空时返回 `[]`。

**下一步还能优化**：
1. **查询优化进阶**：HyDE（先生成假设答案再检索）、Multi-Query（一个问题生成多个改写 query 并行召回）。
2. **切块进阶**：父子文档（Parent-Child）检索——先用大块定位、再用小块精读；或加 overlap。
3. **知识库工程化**：文档版本管理、增量更新（文档改了自动 re-embed，而不是全量重建）、来源溯源引用。
4. **评估体系**：构建 RAG 评估集，用 `RAGAS`（faithfulness / answer relevancy / context recall）量化效果，而不是靠感觉调阈值。
5. **参数自动调优**：当前 0.70、RRF k=60 都是经验值，用评估集系统化扫参。
6. **成本与延迟优化**：Query 改写换更便宜的小模型、Rerank 模型量化、向量检索换 HNSW 索引（ChromaDB 内置）应对知识库增长。

**核心思想**：RAG 是一个「召回 + 粗排 + 精排 + 生成」的流水线，每一环都可以独立优化。当前项目已把「主链路」跑通，剩余是「工程化 + 可评估」的深化。

## Q87：SSE 连接断了怎么办？如何做断点续传 / 重连？

**推荐回答**：

SSE 协议本身支持**自动重连**：服务端可以在响应里带 `retry` 字段告诉客户端重连间隔，`EventSource` 断线后会自动按间隔重连。但本项目用 `fetch` 手动解析，**没有实现自动重连**。

**断点续传的标准做法**：

1. 服务端给每个事件分配递增 `id:` 字段。
2. 客户端记录最后一次收到的 `id`，重连时通过 `Last-Event-ID` 请求头带上。
3. 服务端根据 `Last-Event-ID` 从断点继续推，不重复、不遗漏。

**对 Flash 的适配**：Flash 是「一问一答」，重连语义和传统「长订阅」不同。更实际的方案是：
- 前端 `fetch` 失败时**整句重试**（重新 POST 同一条消息，用 sessionId 保证幂等）；
- 或降级为「先拿完整回答，再前端模拟打字机」，牺牲一点实时性换可靠性。

**对应设计**：`FlashServiceImpl` 里 `HttpClient` 连接超时 10s、请求超时 5min，`SseEmitter` 也是 5min，但都只做了超时，没有重连逻辑。
